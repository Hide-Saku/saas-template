# AI コーディングエージェント 技術判断ルール

**対象**: Claude (claude.ai), Claude Code, Codex, Antigravity, その他すべての AI コーディングエージェント
**策定日**: 2026-05-27
**ステータス**: MUST(省略不可)

---

## なぜこのルールがあるか

AI エージェントが自分の reasoning だけで技術判断を出すと、以下の失敗パターンに陥る:

- 業界標準パターンを「過剰設計」と誤判定する
- 一見シンプルな選択肢を選んで long-term の運用コストを膨らませる
- 短期視点で「solo dev の心理的負担」を過大評価し、業界エコシステムからズレる
- 同一の質問に対して判断が揺れる(複数セッション間で結論が変わる)

これを防ぐため、**すべての技術設計・アーキテクチャ判断時に以下の4ステップを必ず実行する**。

---

## MUST: 4ステップ判断プロセス

### Step 1. 外部情報による自己分析の検証

自分の reasoning だけで結論を出さない。必ず以下を確認する:

- `web_search` による業界ベストプラクティス調査
- 公式ドキュメント(Next.js / Cloudflare / React / Tailwind 等)の最新推奨
- 現実装事例(GitHub / プロダクション運用例 / 業界専門家のブログ)
- 最終更新が古い情報は要警戒、できるだけ直近1年以内の情報を参照

### Step 2. AI コーディングツール推奨の参照

以下のエコシステム公式 skill / 推奨パターンを確認する:

- **Claude Code 公式 skills**: 特に `cloudflare/workers-best-practices`, `cloudflare/cloudflare` 等の Cloudflare 公式 skill bundle
- **Codex 推奨パターン**: GPT-5.3 Codex で動く公式 / 準公式 skill
- **Antigravity 推奨パターン**: backend profile / web profile 等の推奨スタック

エコシステム整合性は long-term の開発効率に直結する。

### Step 3. 7基準による評価

すべての選択肢を以下の7基準で評価する。**短期最適ではなく long-term の視点で評価する**:

| # | 基準 | 着眼点 |
|---|---|---|
| 1 | 最高の UX | ユーザー体感速度、LCP/FCP、レイアウト安定性 |
| 2 | 最高の UI | デザイン一貫性、レスポンシブ性、アクセシビリティ |
| 3 | 最高の 安全 | セキュリティ、データ保護、認証認可、規制対応 |
| 4 | 最高の 開発効率 | 新機能追加・新アプリ追加時の作業量、認知負荷 |
| 5 | 低コスト 開発 | 初期実装コスト、学習コスト、OSS 活用度 |
| 6 | 低コスト 運用 | クラウド費用、保守工数、障害対応コスト |
| 7 | 最高の 完成度(品質) | プロダクション実証度、業界標準度、保守性 |

各選択肢について7基準で○/△/✕を付け、表で比較する。

### Step 4. 競合時のルール

判断が割れた時の優先順位:

1. **外部証拠 vs 自己分析** → 外部証拠を優先
2. **直感的簡素さ vs 業界標準パターン** → 業界標準を優先
3. **短期効率 vs long-term 効率** → long-term を優先
4. **複数の業界ベストプラクティスが競合** → 自身のスタック(Cloudflare / Next.js Static Export 等)に最も近い実例を優先

---

## 揺れの防止

- 判断が揺れた時は Step 1-3 を**徹底的に再実行**する
- 証拠ベースで確定した結論は、**新証拠が出るまで揺らさない**
- 「やっぱりもう少し考えると...」で reasoning だけ追加して結論を変えない
- 別セッションで同じ質問が来ても、同じ Step 1-4 を踏めば同じ結論に収束する

---

## 適用範囲

**MUST 適用**:
- アーキテクチャ判断(packages 構成、状態管理、フレームワーク選択等)
- ライブラリ・ツール選択(state lib、UI lib、test framework 等)
- セキュリティ実装(CSP、auth、CSRF、headers 等)
- インフラ判断(ホスティング、CDN、DB、storage 等)
- 命名・抽象化レベル(package 名、API 設計、データモデル等)

**省略可**:
- 単純な実装作業(既に方針が確定したコードを書くだけ)
- 既存パターンの踏襲(同プロジェクト内で確立済みの方法を使う)
- 緊急対応(障害時の即応で、後で振り返って再評価する前提)

---

## 参考フレーズ(エージェントが応答時に使うべき言い回し)

判断の根拠を明示する時:

- 「web_search で確認した外部情報によると...」
- 「業界標準パターン(◯◯の例)では...」
- 「Cloudflare 公式 skill バンドル推奨では...」
- 「7基準で評価すると、N/7 で◯◯が優位」

判断の揺れを認める時:

- 「Step 1 の外部証拠取得を省略していたので再評価する」
- 「短期効率に振れすぎていたので long-term 視点で再判断する」
